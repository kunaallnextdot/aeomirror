# Phase 1 — Implementation Plan (PLAN ONLY — not implemented in this task)

Scope: take the free scanner to production-grade infrastructure per
`INTEGRATIONS.md` sections **A1 Postgres**, **A2 Alembic**, **A3 Redis**, and
**B1 Email**. This document is a plan for review. **No Postgres/Alembic/Redis/ESP
work has been implemented, and no real provider credentials have been added.**

Guardrails carried from Phase 0:
- The free scanner must never call an LLM or any paid API.
- Do not change the scoring rubric, weights, or the API response contract.
- Never print or commit `.env` secrets.

- `backend/.env` (local, gitignored) — set `DATABASE_URL` to Postgres.
- `backend/.env.example` — add a commented Postgres example (no real creds).
- `backend/requirements.txt` — uncomment `psycopg2-binary==2.9.9`.
- `backend/app/db/session.py` — no logic change expected; the `sqlite`-only

  (`pool_size`, `pool_pre_ping=True`) for a server engine.

  `Integer`, `DateTime`) and is already Postgres-compatible.

**Dependency changes**
- Enable `psycopg2-binary` (already listed, commented).

**Env vars**
- `DATABASE_URL=postgresql+psycopg2://<user>:<pass>@<host>:5432/aeomirror`
  (value provided via secret manager / local `.env`, never committed).

**Migration order**: do A1 **before** A2 is applied against a real DB, but land
the Alembic tooling (A2) so the Postgres schema is created by a migration, not by
`create_all`.

**Rollback**
- Revert `DATABASE_URL` to the SQLite default; the app runs unchanged.
- Keep the SQLite path working in dev/tests (do not hard-code Postgres).

**Tests**
- Existing 11 tests must still pass against SQLite (CI default).
- Add a CI job (or documented local step) that runs the suite against a
  disposable Postgres (service container) to catch dialect drift.

**Acceptance criteria**

  retrievable via `GET /v1/scan/{id}`.
- Full test suite green on both SQLite and Postgres.

**Security**

- `requester_ip_hash` stays hashed (already enforced in `routes_scan.py`).

  (currently `app/main.py:25-28`); migrations become the source of truth.

**Dependency changes**

**Migration order**
1. Introduce Alembic and autogenerate `0001_initial` matching the **existing**

2. Verify `alembic upgrade head` on a fresh DB yields the same schema `create_all`

**Rollback**

- Emergency: re-enable `init_db()` behind the env flag to unblock dev.

**Tests**
- Test bootstrap still creates tables (tests may keep `create_all` via the flag,
  or run `alembic upgrade head` in a fixture).
- Add a check that models and migrations are in sync (autogenerate produces an
  empty diff).

**Acceptance criteria**
- `alembic upgrade head` provisions the schema on a clean Postgres.
- Production no longer calls `create_all`.
- 11 existing tests still pass.

**Security**: migrations run as a controlled deploy step, not on public request.

## A3 — Redis (replace in-memory cache + rate limiter)

**Files likely to change**
- `backend/app/core/cache.py` — reimplement `TTLCache.get/set` and
  `RateLimiter.check` against Redis. **Keep the exact method signatures** so no
  call site changes (`routes_scan.py` uses `scan_cache.get/set` and
  `rate_limiter.check` unchanged).
- `backend/app/config.py` — already has `redis_url: str | None`; add any needed
  key-prefix/TTL settings.
- `backend/.env` / `.env.example` — `REDIS_URL`.
- `backend/requirements.txt` — uncomment/add `redis==5.0.7`.

**Design notes**
- Cache: store the serialized report under the normalized-URL key with a TTL =
  `cache_ttl_seconds`. Note the current in-memory cache stores a live Python
  object (`report`); the Redis version must serialize (the persisted DB `result`
  dict is the natural shape). Keep the returned shape identical to today.
- Rate limiter: replace the per-process list with an atomic Redis counter
  (fixed-window `INCR`+`EXPIRE`, or a sorted-set sliding window). Must return the
  same `(allowed, remaining)` tuple.
- **Fallback:** if `REDIS_URL` is unset, keep the in-memory implementations so
  local dev and tests need no Redis.

**Dependency changes**: add `redis`.

**Migration order**: after A1/A2 (Redis is orthogonal but should land once the DB
is stable). No data migration — cache/limits are ephemeral.

**Rollback**: unset `REDIS_URL` → app falls back to in-memory; no data loss.

**Tests**
- Keep existing in-memory tests (default path).
- Add tests behind a Redis service container: cross-process cache dedupe and rate
  limits shared across workers (the whole point of the swap).

**Acceptance criteria**
- With `REDIS_URL` set and >1 worker, a duplicate URL within TTL is served from
  the shared cache, and the per-IP limit is enforced across workers.
- Behavior with `REDIS_URL` unset is byte-for-byte the current in-memory behavior.

**Security**: authenticated Redis (TLS/ACL) in prod; namespaced keys; never store
raw IPs (only the existing hash).

## B1 — Email provider (welcome / report email)

**Files likely to change**
- `backend/app/services/leads.py` — replace the `send_welcome_email()` print stub
  (`leads.py:27-37`) with a real ESP call. `capture_lead()` already stores the
  lead; only the send is stubbed.
- `backend/.env` / `.env.example` — add `RESEND_API_KEY` (or SES/Postmark equiv).
- `backend/requirements.txt` — only if the chosen ESP needs an SDK; a plain
  `httpx` POST (already a dependency) avoids a new dep.

**Design notes**
- Make the send **non-blocking / best-effort**: a failed email must not fail the
  lead capture or the scan response. Wrap in try/except, log failures, consider a
  background task/queue later.
- Idempotency: avoid re-sending on repeat scans (`scan_count` already tracks this).

**Dependency changes**: none required if using `httpx`; otherwise the ESP SDK.

**Env vars**: `RESEND_API_KEY` (or provider equivalent) — via secret manager.

**Migration order**: independent; can land any time after A1.

**Rollback**: revert `send_welcome_email()` to the no-op/print stub; lead capture
is unaffected.

**Tests**
- Unit test with the ESP call mocked: assert it is invoked with the right args and
  that a send failure does not raise out of `capture_lead()`.
- Do not hit the real ESP in CI.

**Acceptance criteria**
- New lead on scan #2 triggers exactly one real email; failures are swallowed and
  logged; `POST /v1/lead` still returns `{ "ok": true }`.

**Security**: API key via env only; never log the key or full recipient PII beyond
what is necessary; respect unsubscribe/compliance before broad sends.

## Recommended sequence of work

1. **A1 Postgres** — point at Postgres, confirm suite green on both engines.
2. **A2 Alembic** — add tooling, autogenerate `0001_initial`, then remove
   `create_all` from startup. (A1+A2 together = production DB story.)
3. **A3 Redis** — swap cache + rate limiter behind the unchanged interfaces, with
   in-memory fallback when `REDIS_URL` is unset.
4. **B1 Email** — wire the ESP in `send_welcome_email()`, best-effort + tested.
5. Regression pass: all 11 existing tests green; new Postgres/Redis/email tests
   added; `npm run dev` and `npm run test:backend` unchanged for developers.

## Explicitly out of scope for Phase 1
- Auth, billing/Stripe, paid prompt simulation, fix generation, competitor
  monitoring, paid dashboards (Steps 5–6). Not touched.
- Any change to the scoring rubric, weights, or API response contract.
